# v1 Modules Architecture

This directory contains the Application and Infrastructure layers of the Nexus API, organized into self-contained, domain-driven modules. Each module encapsulates a specific business context, ensuring high cohesion and low coupling across the system.

## Design Philosophy

The architecture strictly follows **Clean Architecture** principles and **Domain-Driven Design (DDD)**:

1.  **Layered Isolation:** Dependencies flow inward. The Domain layer (Entities) is the core, followed by the Application layer (Use Cases), and finally the Infrastructure layer (Persistence/External Services).
2.  **Module Decoupling:** Modules are independent. Cross-module communication is handled exclusively through injected interfaces or by calling the exported Module Controller of another module.
3.  **Encapsulation:** Internal implementation details (Use Cases, Repositories, Domain logic) are hidden. Only the `index.ts` file and the wired `ModuleController` are exposed as the public API of the module.
4.  **Contract-First:** Data structures and DTOs are governed by Zod/cz schemas to ensure end-to-end type safety.

## 🤖 AI Agent Directives

Strict adherence to these rules is mandatory for all autonomous agents:

1.  **Public API Only:** Never import from a module's internal directories (`/domain`, `/useCases`, `/infrastructure`). Only import from the module's root `index.ts`.
2.  **Dependency Rule:** Domain entities must never depend on infrastructure. Repositories must implement interfaces defined in the domain.
3.  **Controller Sovereignty:** All operations must pass through the `ModuleController`. Presentation layers (Routes) must never instantiate Use Cases directly.
4.  **Entity Integrity:** Domain entities MUST use `private constructor` and `static create/hydrate` factory methods. State mutation must be controlled via explicit methods, never direct property access.
5.  **Constructor Injection:** Always use constructor injection for dependencies. Do not use global singletons or hardcoded instances within Use Cases or Controllers.
6.  **No Logic in Infrastructure:** Infrastructure adapters must strictly map data between the DB schema and Domain Entities. Business logic in the infrastructure layer is a critical violation.
7.  **Strict Typing:** Ensure all DTOs and return types are strictly typed. Use Zod schemas from the API Contracts package whenever possible.
8.  **Atomic Use Cases:** Each Use Case class should represent a single, atomic business operation.
